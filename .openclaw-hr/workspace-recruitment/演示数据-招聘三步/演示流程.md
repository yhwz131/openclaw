# 招聘主链演示流程 · 三道脚本闸

- 数据目录：`workspace-recruitment/演示数据-招聘三步/`
- 命令都在 `workspace-recruitment` 根目录执行，经 `scripts/recruitment-run.sh` 进入
- 目的：证明主链上三道脚本闸各自有效——模型的产出对不上，脚本就拦住或改回
- 主链顺序：解析 → **闸1 字段回核** → **闸2 敏感字段删除** → 评分 → **闸3 数字回核** → 画像
- 每道闸都用「同一份输入，只改一处」对照：坏的被拦，好的通过
- 【】内为动作，不念
- 台上快捷命令（在 `workspace-recruitment` 根目录执行，内容与下文闸1、闸2 的长命令相同）：
  - `bash 演示数据-招聘三步/闸1-字段回核.sh`：原样，应通过
  - `bash 演示数据-招聘三步/闸1-字段回核.sh 改学校`：应拦下
  - `bash 演示数据-招聘三步/闸2-敏感字段删除.sh`：删干净，自检剩余 0

---

## 开场（约 20 秒）

招聘主链上，模型负责写和抽，过不过由脚本说了算。主链上有三道脚本闸，我一道一道证明。

---

## 闸1 · 字段回核：解析结果对不上原文，就拦下（约 70 秒）

解析简历是模型做的，它有补全的习惯，原文没有的字段也会填一个看起来合理的值。所以解析之后先逐字段回溯原文。

脚本：`skills/auditing-extraction/scripts/audit_extraction.js`。硬提取字段必须能在简历原文里逐字找到。

【打开 `parsed/员工1-后端开发.json`，指 education.school】这是员工1 的解析结果，学校是「某某大学1」。

【运行】

```bash
bash scripts/recruitment-run.sh node skills/auditing-extraction/scripts/audit_extraction.js \
  演示数据-招聘三步/parsed/员工1-后端开发.json \
  演示数据-招聘三步/inbox/resume-tech-员工1-后端开发.md
```

【指终端】硬提取字段 22/22，追溯率 100%，退出码 0，通过。报告落在 `audited/员工1-后端开发.audit.json`。

【打开 `parsed/员工1-后端开发-学校被改.json`】现在我只改一个字段：学校改成「清华大学」，其余一个字不动。简历原文里没有这个学校。

【运行同一条命令，输入换成 `parsed/员工1-后端开发-学校被改.json`】

【指终端】21/22，退出码 1。它点名 `education.school = "清华大学"`，注明在原文找不到出处。其余 21 个字段照样通过，拦得精确。

这一道闸不调用模型，同一个输入永远是同一个结果。对不上的，只能重抽或者人工确认，不能改 JSON 蒙混。

## 闸2 · 敏感字段删除：敏感字段物理删掉，删不干净就不许评分（约 60 秒）

字段是真的，也不等于能拿去评分。《就业促进法》不许就业歧视，年龄、性别这些字段在评分之前必须去掉。

【打开 `test-fixtures/demo-lifecycle/planted-sensitive-员工1-full.json`】这是一份故意埋了敏感字段的样本：年龄 38、性别男、婚育已婚已育、户籍、民族、政治面貌，还有 `education.school_tier` = 985。

脚本：`skills/filtering-sensitive-fields/scripts/filter_sensitive.js`。它递归删除黑名单里的键，删完再自己检查一遍，有残留就退出码 1，这份数据不许进评分。

【运行】

```bash
bash scripts/recruitment-run.sh node skills/filtering-sensitive-fields/scripts/filter_sensitive.js \
  演示数据-招聘三步/test-fixtures/demo-lifecycle/planted-sensitive-员工1-full.json \
  演示数据-招聘三步/scoring/demo-脱敏后-员工1.json
```

【指终端】报出删除了多少个敏感字段，合规自检剩余 0，退出码 0。

【打开 `scoring/demo-脱敏后-员工1.json`，搜索「年龄」「性别」「985」】一个都搜不到。原始那份样本没有被改动，评分模型只看这份脱敏副本。

这一道闸同样不调用模型。

---

## 闸3 · 数字回核：评分里的数字对不上简历，就抓出来（约 90 秒）

评分是模型写的。两份文档同时在上下文里，它会把数字串台。

【打开 `scoring/results/ranking-员工1-后端开发.json`，指抗压能力】这里写着「电商大促峰值58万笔/秒」。

【打开简历 `inbox/resume-tech-员工1-后端开发.md`，搜索 12.8】简历原文是「大促峰值 12.8 万 TPS」，没有 58 万。

【打开 `jds/jd-bigtech-后端开发工程师.md` 第 18 行】58 万在岗位 JD 里：「去年双十一订单峰值 58 万笔/秒」。模型把 JD 的数字安到了候选人头上。

先看没有这道闸会怎样。【把 `scoring/number_audit.py` 的 `verify_in_resume`（约第 140 行）改成 `return True`】比对函数一律回答「简历里有」。

【运行】

```bash
bash scripts/recruitment-run.sh python3 演示数据-招聘三步/scoring/number_audit.py \
  演示数据-招聘三步/inbox/resume-tech-员工1-后端开发.md \
  演示数据-招聘三步/scoring/results/ranking-员工1-后端开发.json
```

【指终端】存疑 0 个，打印「未发现数字虚构」。58 万就这样放过去了。这一步不调用模型。

【把函数改回】

```python
def verify_in_resume(token, resume_norm):
    token_norm = _norm(token)
    if token_norm in resume_norm:
        return True
    num_only = re.match(r"\d+(?:\.\d+)?", token_norm)
    if num_only and num_only.group() in resume_norm:
        return None
    return False
```

【再跑同一条命令】

【指终端前半段】这一段是确定性的：提取 23 个数字，存疑 11 个，其中 58 万被标成「简历无此数字」，字段是 `dimension_reasons.抗压能力`。

后面它把存疑清单交给模型逐个判定，这一步要调用模型，大约一分钟。判定为虚构的处数每轮会浮动，台上只讲 58 万这一处：它每轮都被判为虚构，真实值给回「12.8 万 TPS」。

这条命令只打印、不改文件。改回后的评分用事先留好的文件展示：`scoring/results/ranking-员工1-后端开发.audited.json`，同一栏已经是「12.8 万 TPS」。综合分不改，改的只是被写错的数字。

## 收尾 · 画像只渲染过闸的结果（约 30 秒）

三道闸都过了，才拿去生成画像。画像脚本不调用模型，只渲染已有的 JSON。

```bash
bash scripts/recruitment-run.sh python3 skills/generating-candidate-profiles/scripts/generate_profile.py \
  演示数据-招聘三步/scoring/results/ranking-员工1-后端开发.audited.json \
  员工1 演示数据-招聘三步/profile/output/profile-员工1-回核后.html
```

【浏览器打开 HTML】八维雷达都在，页面上没有年龄、没有性别，评级只是建议。

三道闸合起来就是一句话：字段对不上原文的不放行，敏感字段进不了评分，评分里的数字对不上简历的改回来。模型负责写，脚本负责核。
