# 入职模块技能演示：7 页跨部门编排版大纲及逐字稿

> 主命题：把跨部门、长周期、多人负责的入职事项，编排成一条不会越权、不会丢状态、不会假完成的流程。  
> 核心机制：Lobster 的 `halt / resumeToken / approval / when`。  
> 辅助价值：合规控制、催办减负、查询与看板。  
> 建议时长：设计按 8 分钟，现场含页面切换和人工回复约 10 分钟。  
> 演示对象：员工2｜前端工程师｜30K（彩排前以 HCM 为准）。  
> 与完整流程边界：本段直接进入入职 Agent，不展示 Router；完整流程段只用员工1做一次进度查询，不改 HCM、不走审批、不讲 Lobster。

## 第 1 页｜模块全景：一条员工时间轴

### PPT 标题

**入职不是清单，而是一条跨部门时间轴**

### 页面结构

```text
入职前准备          报到审批              入职后跟进
────────────────────────────────────────────────
HCM 五部门节点  →  Lobster 两道人工门  →  7/30/60/90
合同/账号/设备      合同门 · 账号权限门     到期提醒
Buddy / 培训         resumeToken 恢复       HR 回填
                    ↓
                 入职看板（三类状态汇总，不编造）
```

### 四个承担者

| 承担者 | 负责什么 | 不负责什么 |
|---|---|---|
| HCM | 员工档案与五部门准备事实 | 不存审批 token |
| Lobster | 审批顺序、暂停、恢复 | 不替部门填写 HCM |
| reviews.json | 试用期跟进开通与回填 | 不决定是否录用 |
| 入职小慧 | 读取、催办、推进、提醒 | 不代批、不写 HCM |

### 逐字稿

“招聘确认录用之后，才进入入职模块。入职不是一张待办清单，而是一条跨部门时间轴。

入职前，五个责任部门在 HCM 上推进合同、账号、设备、Buddy 和培训；报到前后，Lobster 控制两道人工审批门；报到之后，系统在 7、30、60、90 天继续跟进。看板只汇总这三类真实状态，不替任何一方编造结果。

本段直接进入入职 Agent。后面完整流程联调才会回到 Router，那时只用一次简单查询验证分发，不再重复审批机制。”

### 用时

约 50 秒。

## 第 2 页｜入职为何困难：多人、多状态、两类高风险决定

### PPT 标题

**状态分散、责任分散，模型最容易说“已经办完了”**

### 五个责任部门

合同签署 · IT 账号 · 行政设备 · Buddy 匹配 · 入职培训

### 三类状态源

1. HCM：部门是否真的开始或完成。  
2. Lobster：审批是否暂停、谁在决定、能否恢复。  
3. reviews.json：试用期跟进是否开通、到期、回填。

### 两类高风险决定（穿插法律）

| 决定点 | 风险 | 设计依据 | 项目机制 |
|---|---|---|---|
| 合同条款 | 劳动关系成立与条款责任 | 《劳动合同法》第八、十条 | 合同节点作启动守卫；合同门强制人工审批 |
| 账号权限 | 真实系统访问边界 | 现行《网络安全法》第二十三条 | 账号权限门强制人工审批；材料不足不建议批准 |
| 员工数据读取 | 过度读取或旧快照冒充 | 《个人信息保护法》第六、十三条 | HCM 只 GET、按人按节点读取；不可用即停止 |

> 准确口径：两道人工门是项目依据业务与法律风险设计的控制机制，不是法律条文原句。

### 逐字稿

“入职难在状态分散和责任分散。五个部门各自更新 HCM，审批状态又在 Lobster，试用期跟进还在本地表。如果让模型根据对话判断“已经办完了”，最容易产生假成功。

因此系统把状态拆开：HCM 管业务事实，Lobster 管审批推进，本地表管后续跟进。合同关系到书面劳动合同和告知义务，账号开通关系到未授权访问风险，所以这两类决定必须由人完成。员工数据则按目的和最小必要读取，HCM 不可用就停止，不拿旧快照冒充。”

### 用时

约 70 秒。

## 第 3 页｜现场协同起点：等待部门，而不是替部门执行

### PPT 标题

**合同未开始：流程拒绝启动，等待真实部门更新**

### 现场动作

1. 直接对入职 Agent 输入：  
   > 请为员工2启动入职流程，岗位是前端工程师，薪资 30K。
2. 观察合同节点仍为 `pending` 时：  
   - `start` 退出 6  
   - `workflow.json` 记 `waiting_departments`  
   - 明确催办 HR / 合同责任部门  
   - **不调用 Lobster**
3. 队友在 HCM 将员工2合同节点更新为 `in_progress` 或 `completed`。
4. 再次启动：通过前置校验，进入 HCM 只读快照，随后交给 Lobster。

### 机制重点

- 小慧不向 HCM 做 POST/PUT。  
- 本地快照只服务当次流程，不替代 HCM。  
- “等待部门”是合法状态，不是演示失败。

### 逐字稿

“现在用员工2启动入职。当前合同节点仍是 pending，系统不会假装已经开始，而是退出并记录 waiting_departments，催责任部门在 HCM 更新。

请队友在 HCM 把合同节点改成进行中。再次启动后，小慧只读真实进度，再进入 Lobster。这一步证明：跨部门协同的第一原则，是读取真实状态，而不是替部门执行。”

### 用时

约 2 分钟（含 HCM 更新）。

## 第 4 页｜Lobster 核心机制：可暂停、可恢复的人工审批

### PPT 标题

**机制重点：Lobster 把人工决策写成不可跳过的节点**

### Lobster 调用链

```text
入职 Skill
  → run-onboarding.sh
    → Lobster 读取 hr-onboarding.lobster
      → prep → contract_gate → account_gate → buddy → complete
```

### 工作流核心语义

```yaml
- id: contract_gate
  run: build-approval-prompt.py contract
  approval: true          # 自动 halt

- id: complete
  when: $contract_gate.approved && $account_gate.approved
```

- `run`：调用脚本读取状态、生成审批正文、写事件。  
- `approval: true`：运行到门后自动暂停。  
- `when`：两道门都批准，后续节点才执行。

### 现场必须看见

- `status = needs_approval`  
- `current_step = contract_gate`  
- 审批正文原样展示  
- 本次专属 `resumeToken`  
- HR 主管批准后：`resume <token> yes`，从暂停点恢复，不重跑整条链路

### 工程封装（简要）

- `start / resume / dry` 统一入口  
- 按拼音隔离 `stub-state/<pinyin>/`  
- token 回填 `workflow.json`  
- `approval:` 不做参数模板替换，因此由 `run` 动态生成专属 prompt

### 逐字稿

“进入 Lobster 后，流程先做 HCM 快照，然后停在合同审批门。approval true 让节点自动 halt；run 生成给 HR 主管看的审批正文；小慧必须原样展示，不能总结后代替。

屏幕上可以看到 needs_approval、contract_gate 和本次 resumeToken。HR 主管批准后，使用这个 token 从暂停点恢复，而不是重新启动整条流程。流程状态不依赖模型记忆，审批节点也不能被跳过。”

### 用时

约 2 分钟。

## 第 5 页｜第二道门与防假完成

### PPT 标题

**账号权限门＋双重完成：拦住两类假成功**

### 第二道门

```text
contract_gate 批准
    ↓
account_gate 暂停（新 resumeToken）
    ├─ 拒绝 → cancelled
    └─ 批准 → workflow complete
```

- 审批人：IT 安全负责人。  
- 账号、设备、培训仍待办时，不建议批准。  
- 每道门生成新 token，旧 token 和 `approvalId` 都不能代替。

### 双重完成

```text
Lobster 两门均批准     → 审批流程 complete
HCM 五节点全部 completed → 部门准备完成
              两者同时满足
                     ↓
            sync-reviews-if-ready
                     ↓
          开通 7 / 30 / 60 / 90 天跟进
```

### 现场验证点

展示或口述一种未全绿状态：  
即使 `workflow = complete`，只要任一 HCM 节点未完成，`sync-reviews-if-ready` 跳过，不挂 Cron。

### 逐字稿

“合同门通过后，流程进入账号权限门，并生成新的 resumeToken。这一道门由 IT 安全负责人决定，因为账号开通后会产生真实访问权限。

但两道门都批准，只说明审批流程走完，不等于电脑、Buddy、培训都已落实。系统设置第二个阈值：HCM 五节点也必须全部完成，才会开通试用期跟进。未全绿就不挂 Cron。这样拦住审批假成功。”

### 用时

约 1 分 40 秒。

## 第 6 页｜Cron 到期主动推送飞书

### PPT 标题

**到期不是自动完成：Cron主动催办，HR回填闭环**

### 触发链路

```text
HCM 五节点全绿
→ sync-reviews-if-ready
→ 注册 7/30/60/90 四个一次性 Cron
→ 到期在 onboarding 隔离会话运行 review
→ 飞书 announce 推送重点与待回填原因
→ HR 确认后执行 CLI record
```

### 截图证据

右侧展示员工2第7天真实飞书推送：

- HCM总体状态：`onboarding`；
- 五部门节点：全部 `completed`；
- Review状态：`due`，尚未回填；
- 本次重点：公司级Onboarding、导师启动带教、融入团队；
- 推送成功不等于跟进完成。

### 异常守卫

- 员工总体状态为 `cancelled`：不开通或追加跟进；
- 已存在任务触发时，也不输出 `needs_review` 催办；
- 飞书只负责通知，不直接修改 `reviews.json`。

### 逐字稿

“五节点全部完成后，系统注册第7、30、60、90天四个一次性Cron。到期任务在入职Agent的隔离会话运行review脚本，再通过飞书主动推送。

右侧是员工2第7天的真实消息：HCM五节点全部完成，Review状态仍为due，因为HR还没有回填。它证明推送链路已运行，也证明推送成功不等于跟进完成。

只有HR完成真实沟通并在CLI回填后，状态才会改变。员工总体状态如果已经cancelled，系统会停止跟进，不再催办。”

### 用时

约 1 分钟。

## 第 7 页｜入职后闭环与证据收束

### PPT 标题

**跟进只提醒，完成靠回填；所有结论都能追溯**

### 试用期跟进

- 第 7 / 30 / 60 / 90 天。  
- Cron 到点只产生 `needs_review`。  
- HR 确认真实沟通后，才 CLI 回填完成。  
- 查询和看板刷新只读，不挂 Cron。

### 证据区

- `workflow.json` 事件：halted → approved → complete  
- 入职看板：五节点进度与审批角标分开显示  
- 不在本页重新演示自然语言查询（留给完整流程联调）

### 与完整流程的交接语

“入职机制已经验证完毕。后面完整流程联调时，会从 Router 入口查询员工1的入职进度，只验证正确分发和结果返回，不再重复两道审批门和 HCM 更新。”

### 逐字稿

“入职后跟进同样防止假成功：到期只提醒，HR 回填后才记录完成。右侧是真实运行事件和看板证据。

入职模块的价值，是把跨部门状态编排成可控流程：状态来自真实系统，顺序由 Lobster 控制，关键决定由人完成，结果全程可追溯。机制演示到此结束，完整流程段不再重复这些动作。”

### 用时

约 50 秒。

## 七页衔接

1. 第1→第2：“时间轴清楚以后，为什么必须拆开状态和责任。”  
2. 第2→第3：“先看现场最常见的协同场景：部门还没更新，系统怎么处理。”  
3. 第3→第4：“部门更新之后，Lobster 怎样把决定交给人。”  
4. 第4→第5：“第一道门通过后，第二道门和业务完成怎样继续把关。”  
5. 第5→第6：“两个完成条件满足之后，系统怎样在到期时主动找到HR。”  
6. 第6→第7：“推送链路验证完成，最后用事件和看板收束并交接完整流程联调。”
