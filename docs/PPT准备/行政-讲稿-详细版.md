# 行政模块讲稿（详细版）

> 对应 PPT：第 20–24 页（第 24 页用「两层把关版」）。

## 开场过渡（从入职切到行政，约 10 秒）

「前面招聘解决的是『说得不准』，入职解决的是『做得越界』。行政解决第三道坎：**查得不清**——数据该给谁、答案出自哪里。我们的办法是两个词：**分权、有据**。」

## 第 20 页 · 行政 Agent 业务全貌（约 40 秒）

【指页面三行业务，从上往下】

「行政 Agent 面对两类人：员工来问制度，HR 来查数据。一共三项业务。

**第一，制度答疑。** 员工在飞书提问，脚本先去 14 份制度里检索，**检索不到就直接退出**，模型拿不到原文就没法编；检索到了，模型照原文作答、标出处；个案和争议转给 HR。

**第二，员工数据查询。** 飞书消息进来，网关先记下是谁发的，再按发送人分配工具；真正读数据之前，闸门脚本先判身份，不是 HR 就以退出码 3 结束，HR 过了闸才读 HCM。

**第三，HR 月报。** 6 张台账由脚本算出 18 个指标，每个数字回核到来源；模型只负责转述和解释口径，不改数；HR 审阅后再用。」

【点一下页面上的「模型 / 脚本 / 人」图例】

「大家可以看每一行的颜色：**模型只出现在『写』的位置，检索、判身份、算数字全是脚本，最后决定的是人。** 这就是我们项目的主线，后面我会用行政把它讲透。」

## 第 21 页 · 风险：法与规（约 50 秒）

「为什么要这样设计？对应两条法、一条规。

**分权，管的是人与人之间。** 《个人信息保护法》第六条要求最小必要，第五十一条要求合理确定操作权限。风险是：员工查同事的敏感数据，Agent 照查照答——Agent 是能读 HCM 的，如果不分权，它就成了越权的通道。

**有据，管的是人与 Agent 之间。** 企业的规是：答制度要说清出自哪份制度，答错能查到原因；争议、法律定性、审批，判断权在人。风险是：Agent 凭常识说出不符合公司制度的答案，员工照着做，引发纠纷。

所以我们的分工是：**模型按原文作答，脚本按身份放行，人去定个案与争议。**」

## 第 22 页 · 有据机制（约 50 秒）

【顺着 ①②③④ 讲】

「有据分四步：

① **先判断该不该答。** 这是第一步，不是最后一步——检索得到相关政策，不等于这个问题该由 Agent 回答。
② **检索 IMA 制度库原文**，14 份制度，找不到就停。
③ **按原文作答**，不补常识、不改数字。
④ **标出处**，末尾写『政策依据：《…》』。」

【指右下五类红线】

「红线一共五类：个人数据、个案争议、法律定性、无依据、审批决定。判断红线有两层：

- **脚本先按关键词硬过滤**，比如『仲裁、维权、克扣、特批』，命中就必须转人工——这一步不问模型同不同意；
- **模型再按语义判断**，员工说得口语化、没碰关键词，模型也能认出来。

也就是说，**关键词兜底是脚本的，语义理解是模型的**，两个叠起来。」

## 第 23 页 · 分权机制（约 1 分钟）

「分权看一句话进来走六跳，三行是三种身份，都是系统里的真实记录。」

【先讲第一、二行】

「员工和 HR 发的是同一句『请查询员工1的合同薪资』。前四跳完全一样：都进行政 bot，模型都发出同一种命令，执行白名单都放行。区别在第五、六跳：**身份反查**按网关会话记录认人，**闸门**比对 HR 名单——员工 exit 3，一条数据都没读；HR exit 0，读到 HCM。」

【停下来，重点讲第三行「冒充」】

「最关键的是第三行。假设模型被话术骗了，在命令里**改填了 HR 的 ID**。命令看起来是 HR 发的，但网关会话记录里记的是员工，闸门按记录判，照样 exit 3。

**模型说自己是谁不算数，系统记录说是谁才算数。** 这就是分权不靠模型自觉的原因。」

过渡：「上一页看到了结果，下一页我们现场跑一遍，再打开代码看每一步是谁在做。」

## 第 24 页 · 现场证明 + 两层把关（约 4–5 分钟）

### 一、现场演示（约 2 分钟）

【飞书私聊行政小慧】

**有据（员工账号）**：「现场看两点：**答案标注出处**、**红线问题转人工**。」

- 问一个制度问题 → 指回复末尾的「政策依据：《…》」。
- 问一个带个案或维权的问题 → 指回复里通用规则照答、个案明确转 HR。

**分权（先员工、再 HR，同一句话一字不改）**：「**同一句话，换个身份，答案不同。**」

- 员工 → 被拒，没有任何数据。
- HR → 读到花名册。

### 二、整体介绍两层（约 30 秒，停在流程图上）

「刚才的结果是怎么来的？我们的保护分两层。

**上层是软保护**：SOUL、AGENTS、TOOLS 三个文件，告诉模型『你是谁、这事走哪个技能、命令怎么写』。它靠模型自觉，能挡住绝大多数正常情况，但模型可能判错、可能被带偏。

**下层是硬保护**：网关配置加闸门脚本，导师叫它『编码式路由』——该走哪条路、能不能拿数据，写死在配置和代码里，不由模型决定。

一句话：**上层让模型尽量做对，下层保证模型做错了也拿不到数据。**」

## 升到全局：以行政为例，讲项目怎么做到「模型写 · 脚本核」（约 1 分半钟）

### 1. 先用行政把三个字说清楚

「我们项目的口号是『模型写，脚本核，人定』。行政三项业务正好是三种写法：

| 业务     | 模型写什么             | 脚本核什么（失败就停）                                               | 人定什么             |
| -------- | ---------------------- | -------------------------------------------------------------------- | -------------------- |
| 制度答疑 | 照原文组织回答、标出处 | 红线关键词命中必须转人工；**检索无命中就退出**，模型拿不到原文 | 个案、争议、法律定性 |
| 数据查询 | 写出查询命令           | 白名单只放一个入口；**按会话记录认人，非 HR exit 3**           | HR 拿到数据后怎么用  |
| HR 月报  | 转述结果、解释口径     | 脚本算 18 个指标，**每个数字出回核表**对到 CSV 来源            | HR 审阅后使用        |

**规律是：模型写出来的任何东西，都必须过一道脚本才能变成结果；脚本只用退出码说话，0 才往下走。**」

### 2. 为什么说『脚本核』是真的在起作用

「刚才大家已经看到两个证据：

- 第 23 页的『冒充』——模型被骗、在命令里改填了 HR 的 ID，闸门按会话记录照样拒绝。**模型写错了，脚本没让它过。**
- 飞书里同一句话，员工被拒、HR 查到——对应闸门的 3 和 0。**放不放行，是脚本的退出码决定的，不是模型的回答决定的。**」

### 3. 推到其他模块：同一个模式

「这个模式不是行政独有的，五个模块都是：

| 模块 | 模型写                 | 脚本核（失败退出）                             | 人定               |
| ---- | ---------------------- | ---------------------------------------------- | ------------------ |
| 招聘 | 解析简历、八维评分     | 原文回溯、评分前删敏感字段、评语数字回原简历核 | 约面、录用         |
| 入职 | 汇报卡点、转交审批问题 | Lobster 审批门写死在流程里，到门即停           | 合同、账号两道审批 |
| 培训 | 生成培训物料           | 依赖不满足就停、生成后自检                     | 是否采用           |
| 绩效 | 读评语判共识或分歧     | 缺自评即停，分数全部脚本算                     | 主管面谈后定级     |
| 行政 | 照原文作答、写命令     | 检索无命中退出、身份闸门 exit 3                | 个案与争议         |

第 30 页的八道闸门 G1–G8，就是这些『脚本核』逐条实测通过的记录，其中 G6、G7 就是行政：知识库无命中就失败退出；非 HR 查不到他人工资。」

### 4. 收尾

「所以回到开头那句话：**上层三个文件让模型尽量做对，下层网关和闸门保证模型做错了也拿不到数据。** 行政是这样，整个小慧也是这样——模型负责写，脚本负责核，最后由人来定。」
