培训、绩效技能演示部分大纲

整体定位

培训与绩效由同一位成员负责，建议总时长控制在 12—15 分钟：

培训模块：5—6 分钟
绩效模块：6—7 分钟
模块衔接与交接：1—2 分钟

这部分仍然沿用前面已经确定的设计原则：

Agent负责理解与生成，脚本负责校验与约束，HR负责审核与最终决策。

但培训和绩效的侧重点不同：

培训重点解决“生成了很多材料，但不一定是用户要的，也不一定能直接交付”；
绩效重点解决“反馈数据不完整、计算可能漂移，以及Agent越权给员工定级”。


一、培训模块介绍（PPT第1页）

培训Agent的主要作用

培训Agent根据HR点名的培训主题和交付物，从source-docs中的真实素材出发，
按照ADDIE方法组织内容，生成指定的培训资料，并在交付前完成结构自检。

需要特别说明：

系统最多支持生成8类培训物料，但“8类”只是能力上限，不是每次默认全部生成。
用户点名哪几份，Agent就生成哪几份；用户没有要求的资料不擅自生成。

图表内容：

培训需求
→ 点名需要的交付物
→ 读取source-docs真实素材
→ ADDIE阶段编排
→ 生成指定培训资料
→ 结构自检
→ 讲师审核后交付

ADDIE五阶段：

A 需求分析：明确培训对象、痛点和培训目标
D 课程设计：确定模块、时长、教学方式
D 物料开发：生成PPT大纲、讲师手册、学员手册、测试题等
I 培训实施：生成交付指南和实施清单
E 效果评估：生成测试题和评估反馈表

最多支持的8类物料：

1.需求分析
2.课程设计
3.PPT大纲
4.讲师手册
5.学员手册
6.课后测试题
7.交付指南
8.评估反馈表

口播重点：

“培训Agent不是收到一个主题后就一次性生成八份材料，而是先根据HR点名确定本次交付范围，
再按照ADDIE阶段关系组织生成。每份材料都来自已有素材，生成完成后还要经过机器自检和讲师审核。”


二、培训Agent机制实现（PPT第2页）

开发过程中发现的问题

1.用户只需要测试题或评估表时，Agent可能默认生成整套物料，造成不必要的等待和内容堆积。

2.多份材料分别生成时，容易出现前后口径不一致：
课程设计中的目标与PPT大纲对不上，测试题也不一定覆盖前面设定的培训目标。

3.生成完成不等于可以直接交付：
材料可能缺少文件、培训目标、对应矩阵或AI辅助标注，也可能出现讲师手册写成长篇逐字稿的问题。

4.如果source-docs中没有制度、数字或产品资料，模型可能依靠常识补充不存在的内容。

对应机制

机制一：点名生成

使用--only限定本次需要的文件。
用户点名哪几份就生成哪几份，不默认扩展成整套8份。

机制二：阶段承接

后一阶段必须读取指定的前一阶段产物：

需求分析 → 课程设计 → PPT大纲
PPT大纲 → 讲师手册、学员手册
培训目标 + 学员手册 → 课后测试题

通过固定输入关系减少多份材料之间的口径漂移。

机制三：素材边界

只允许读取source-docs中的真实素材。
素材为空时脚本直接停止，不使用模型常识补写制度、数字和公司名称。

机制四：交付前自检

self_check.py负责检查可以机器化验证的结构项：

点名文件是否生成并落盘
是否包含“AI辅助生成”标注
需求分析是否包含T1—T5培训目标
课程设计是否包含目标对应矩阵
测试题是否覆盖T1—T5
讲师手册是否出现禁止的逐字稿正文

必须准确说明：

机器自检只能验证结构项。
“后一阶段是否真正理解并继承了前一阶段内容”等语义问题，
仍需Agent对照eval-cases检查，并由讲师进行最终审核。

培训实操流程

1.展示HR点名的培训需求，例如：
“请围绕新员工入职流程，只生成讲师手册和课后测试题。”

2.展示source-docs中的入职流程素材，说明生成内容只能来自这些文件。

3.展示--only参数的解析结果，确认本次只选择04讲师手册和06课后测试题。

4.运行点名生成流程：

bash scripts/training-run.sh generate --theme 入职流程 --only 04,06

如果目标文件已经存在，需要现场重新生成时使用：

bash scripts/training-run.sh generate --theme 入职流程 --only 04,06 --force

5.查看training-materials/入职流程目录，确认未点名的文件没有被本次流程擅自生成。

6.运行部分物料结构自检：

python3 skills/generating-training-materials/scripts/self_check.py \
  --outdir training-materials/入职流程 --partial

7.查看自检结果、退出码和AI辅助标注。

8.打开讲师手册和测试题，展示：

讲师手册采用讲解要点，不是逐字稿；
测试题标明对应培训目标；
文末标注“AI辅助生成、讲师审核后交付”。

建议展示的失败路径

使用开发中沉淀的错误样本，例如：

删除某份物料中的“AI辅助生成”标注；
或者让测试题缺少T1—T5中的一个目标。

运行self_check.py后应看到：

结构自检FAIL
明确指出缺少的项目
退出码1
不能声称物料已经交付

这里同样应使用“回归测试用例”，不要说“提前准备的错误文件”。

培训模块只展示命令运行、自检结果和产出文件，不安排现场手写代码。
全段唯一的手写代码放在后面的绩效聚合环节。

三、培训模块收口与绩效模块交接

培训部分收口话术：

“通过点名生成、阶段承接、素材边界和交付前自检，
培训Agent解决的不是单纯的内容生成问题，
而是让培训资料按需求生成、前后口径一致，并在讲师审核前先完成机器可检查项的验证。”

随后交接：

“培训资料需要讲师审核，绩效结果同样不能由Agent直接作出最终判断。
接下来我们进入绩效模块，展示小慧如何处理360度反馈中的数据完整性、计算稳定性和定级边界。”


四、绩效模块介绍（PPT第3页）

绩效Agent的主要作用

绩效Agent接收员工的360度反馈材料，
将不同评价视角的数据进行校验、匿名化和聚合，
再生成共识点、分歧点、面谈建议以及可视化看板，
供主管进行绩效面谈和校准会使用。

图表内容：

360反馈压缩包 / DOCX表单
→ 文档解析为JSON
→ 数据完整性校验（重点）
→ 评价人角色匿名化（重点）
→ 五维分数机械聚合（重点）
→ Agent分析共识与分歧
→ 360反馈报告与看板
→ 主管面谈、复核和校准

五个固定维度：

目标达成
专业能力
协作沟通
责任心
学习成长

四类评价视角：

上级
平级
下属
自评

需要准确说明：

系统允许根据实际反馈人数汇总多个平级或下属评价。
聚合前至少必须有上级反馈和员工自评；
缺少必要视角、维度不全或分数不在1—5范围时，脚本拒绝聚合。

口播重点：

“绩效Agent并不替主管给员工定级。它把多份360度反馈整理成主管能够复核的材料：
脚本负责校验和计算，Agent负责理解评语、分析共识与分歧，
最终绩效等级仍由主管复核和校准流程决定。”


五、绩效Agent机制实现（PPT第4页）

开发过程中发现的问题

1.反馈材料可能不完整。

例如缺少员工自评或上级反馈，如果仍然生成结果，
报告就会失去关键视角，无法称为完整的360度反馈材料。

2.绩效分数属于敏感且高影响的数据。

如果让模型直接计算平均分，同一批数据可能出现数值漂移，
也难以说明每个结果来自哪份反馈。

3.评价材料中可能包含真实姓名。

如果直接进入汇总报告或看板，会造成不必要的身份暴露，
也容易让使用者把注意力从反馈内容转向具体评价人。

4.机械极差只能提示“可能存在分歧”，不能直接替代语义判断。

例如各视角平均分极差达到1.0，只能说明需要重点关注；
最终是共识还是分歧，还要结合评价文字进行分析。

5.Agent可能越过辅助边界，直接输出S/A/B/C/D绩效等级。

对应机制

机制一：聚合前数据闸门

check_feedback.py逐份检查：

JSON是否能够解析
reviewer_relation、scores、comments是否齐全
评价关系是否属于manager、peer、report、self
五个维度是否齐全
每项评分是否为1—5整数
是否至少包含一份上级反馈和一份自评

任何一项不通过：

列出全部问题
退出码1
拒绝写出aggregated-data.json

机制二：评价人匿名化

聚合前将评价人统一改写为角色代号：

领导1
同事1、同事2……
下属1、下属2……
自评

真实姓名不进入聚合产物和看板。

机制三：分数机械聚合

平均分、最小值、最大值和视角极差全部由aggregate.py计算。

aggregated-data.json作为后续报告和看板的唯一数字基准。
Agent不能重新计算或修改分数。

机制四：机械信号与语义分析分层

脚本根据“各视角平均分极差≥1.0”标记疑似分歧，
但这只是提醒Agent和主管重点关注。

Agent再读取原始评语，分析：

各方是否真的存在观点冲突
分歧来自工作场景、评价尺度还是信息不足
主管在绩效面谈时可以怎样核实

机制五：不输出绩效定级

报告和看板只展示：

五维分数
不同视角对比
共识点
分歧点
面谈建议

禁止输出S/A/B/C/D最终绩效等级。
最终定级交给主管复核和校准会。

七、全段唯一的手写代码：绩效聚合

建议现场手写“视角平均分与极差计算”核心代码，
体现绩效数字由脚本稳定计算，而不是由模型生成。

示例核心：

def aggregate_dimension(groups, dimension):
    result = {}

    for relation, feedbacks in groups.items():
        scores = [fb["scores"][dimension] for fb in feedbacks]
        result[relation] = {
            "count": len(scores),
            "average": round(sum(scores) / len(scores), 2),
            "min": min(scores),
            "max": max(scores),
        }

    perspective_avgs = [
        item["average"] for item in result.values()
    ]
    perspective_range = round(
        max(perspective_avgs) - min(perspective_avgs), 2
    )

    return result, {
        "perspective_range": perspective_range,
        "suspected_split": perspective_range >= 1.0,
    }

讲解重点：

同一批反馈输入多次运行，平均分和极差保持一致；
极差只标记疑似分歧，不直接生成最终结论；
最终共识、分歧和绩效等级仍需要人参与判断。


八、绩效模块收口与行政模块交接

绩效部分收口话术：

“通过聚合前校验、评价人匿名化和机械计算，
我们保证了绩效数据完整、分数稳定且可以追溯；
Agent只负责分析评语中的共识和分歧，不重新计算分数，也不输出最终绩效等级。”

交接话术：

“绩效数据属于高敏感信息，因此我们把计算和决策边界进行了严格拆分。
接下来进入行政模块，继续展示小慧如何通过身份校验、政策原文检索和月报计算，
处理日常行政问答与数据汇报。”
